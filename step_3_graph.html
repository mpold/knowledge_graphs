Step 3 — graph (high_confidence_g.py; high_confidence.py deprecated)

NB!  kaggle_working.zip must be downloaded to the local computer and unzipped before high_confidence_g.py is triggered.

high_confidence.py is DEPRECATED — use high_confidence_g.py (section 8). It still runs, unchanged, but it is no longer developed and it now understates what step 2 produces: it categorizes graph edges by polarity and never reads predicate.text, so the typed, signed labels from the BioRED checkpoint (upregulator/activator vs downregulator/inhibitor vs binds) all collapse into one indistinguishable edge; and it has no multi-model merge, so with relation_extraction.py --route-mode additive writing up to two triples per entity pair its counts double-count and the higher score silently wins per (pair, sentence) — an implicit “union” policy nobody chose. high_confidence_g.py does both properly (--merge gate|union|typed|none and relation-typed edges). Sections 1–7 below describe the deprecated script and are kept for reference; the one thing it still does that the “G” step does not is the disease/chemical context restriction (rule 5) — apply that by filtering the “G” output rather than reviving this file.

Inputs and outputs of the step-3 analysis that reads the triples the GPU bundle (step 2) produced and draws the interactive graph. high_confidence_g.py (section 8) is the maintained script — one command in, one JSON export plus one self-contained HTML graph out, standalone (not orchestrated by gpu.py). It draws one graph — over gene, DISEASE and CHEMICAL nodes — and writes _M outputs; the gene–gene-only view, and its _G outputs, has been retired. high_confidence.py, the older “G_D_C” variant that required a disease/chemical sentence context, is deprecated; sections 1–7 document it for reference and its file names still appear there. The two output sets are suffixed differently, so nothing clobbers anything in a shared data root.

2. The “G_D_C” qualifying filter — deprecated high_confidence.py

A scored RE triple is kept only when all five conditions hold (qualifies()). This is what separates “high-confidence gene–gene in a disease/chemical context” from the raw scored output.

  1. score ≥ --score — model relation score at or above the threshold (export default 0.8).
  2. control = no — at least one GENETIC endpoint is annotated control: "no" (a studied gene, not a lab control).
  3. not control = yes — neither endpoint is annotated control: "yes".
  4. no MKI67 — neither endpoint's hgnc_symbol is MKI67 (proliferation marker, excluded).
  5. disease/chemical context — the triple's sentence also carries a DISEASE or CHEMICAL entity, per triples.json.

7. Notes — deprecated high_confidence.py

  • Hand-off from step 2. Every required input is a file the GPU bundle (step_2_triples.html) wrote into TRIPLES/; the optional inputs come from the bundle's DISEASE/, CHEMICAL/ and databases/ dirs. This stage is the “step 3” that consumes them.
  • Export threshold vs. graph universe. --score sets the exported JSON's cutoff, but the graph is always built from the score ≥ 0.8 universe (with per-sentence scores kept), so the ≥0.8 / ≥0.95 / ≥0.99 toggle works in the browser regardless of --score.
  • Single-file, portable HTML. The graph inlines both the data payload and (when the fetch succeeds) the vis-network library, so high_confidence.html opens with no build step and no network once written.

8. The maintained step 3 — high_confidence_g.py (the “G” step)

Originally the gene-only sibling of the script above, now the maintained step-3 entry point — and no longer gene-only: the multi-type graph is the only one it draws. Its “G” filter replaced the “G_D_C” filter, and it is the only one of the two that consumes what the BioRED model adds. Its output filenames all carry an _M suffix, so it never clobbers the deprecated script's outputs.

Two things it does that high_confidence.py does not.

1. Typed, signed edges. Each edge is categorized by the relation the model predicted — activates / inhibits / binds / interacts / associated, prefixed not  when the statement is negated — instead of by polarity alone. Colour encodes the relation (green activates, red inhibits, blue binds, purple interacts, grey associated, amber negated), negated edges are dashed, the in-panel filter list is now “Relation type” with live counts (total · N in view — the total is every edge of that type in the file, the second number is how many survive the current score / year / text / min-connections / min-cluster settings, shown red when a ticked type is entirely pruned; Min cluster size now defaults to 2 so a lone two-gene edge is no longer silently dropped), and the tooltip carries each sentence's own label — an edge shows its best-supported relation, so a minority reading stays visible there rather than disappearing.

Negation and speculation are shown differently, on purpose. A tooltip line reading [interacts ?] is not a second relation type — the ? marks speculated modality: that sentence hedges the claim instead of asserting it. It comes from relation_extraction.py's negation_modality(), a cue-list scan of a window around the pair (±40 chars before the subject, ±30 after the object) for may / might / could / likely / possibly / potential / putative / suggest* / appears / seems / propose* / predict* / hypothes* / candidate; the words that fired are kept in assertion_cues in the JSON. 38 sentences carry it in the reference graph, e.g. ASCL1 → small cell lung carcinoma [associated ?] from “…are likely associated with the prognosis of SCLC”.
how it is shownwhy that way
negation
polarity		 folded into the category itself — not interacts — drawn dashed and in amber, and filterable as its own relation type “X does not bind Y” is a different claim from “X binds Y”, so it must not share an edge category with it
speculation
modality		 a ? after the relation in the per-sentence tooltip line only; the edge's own category and colour are unaffected “X may bind Y” is the same claim held more weakly — worth flagging for the reader, not worth splitting the graph over
Both are per sentence, so an edge can rest on three asserted sentences and one hedged one; the edge takes its best-supported relation regardless. And both are kept at full score — neither is dropped nor down-weighted, because a negated or hedged statement is still what the paper said. Flagging beats discarding.

2. A multi-model merge. --merge collapses the two triples an additive RE run writes per pair (binary PPI + typed BioRED, joined on pair_id) into one:

3. The multi-type graph. A gene-only view draws an edge only when both endpoints carry a single HGNC symbol, so everything BioRED adds beyond gene–gene is discarded — on the reference run, 649 of its 655 solo pairs (466 gene–disease, 117 chemical–gene, 29 chemical–disease, 24 chemical–chemical). That is why it was retired. Here DISEASE and CHEMICAL endpoints are nodes too, identified by their normalized id (mondo_label / chebi_label, or ncit_label where ChEBI has no term for the substance) so one entity is one node across documents. Node hygiene reuses the pipeline's own annotations — control for genes, phenotype from DISEASE/disease.json, non_chemical from CHEMICAL/chemical.json — plus two small curated tables and one exclusion list of its own. CHEMICAL_IGNORE keeps out substances ChEBI resolves correctly but that are not compounds under study: tyrosine, whose mentions are the residue being named (“phosphorylation at tyrosine 759”), and glucose, whose mentions are culture conditions (“under low glucose”). The match is exact, so tyrosine kinase inhibitor and 2-deoxy-D-glucose survive. DISEASE_IGNORE drops terms too generic to be a useful node, matched against both the surface text and the MONDO label: neoplasm (the label “tumor”/“tumors”/“tumour” normalize onto — 167 endpoint mentions on the reference run, ~40% of all disease mentions, so removing this entry is how you get them back), cancer (18), and the surface os (“overall survival”, a metric the NER mislabels as DISEASE and which never appears as a MONDO label — a label-only check could never catch it). The match is exact, so breast cancer and lung neoplasm survive. DISEASE_SURFACE fixes mappings that are wrong for this corpus rather than ignoring them: lcc normalizes to leukoencephalopathy with calcifications and cysts, which in a lung-large-cell corpus is large cell carcinoma (6 mentions). DISEASE_MERGE then folds distinct MONDO terms that name the same disease at the same granularity into one node — lung carcinoma and lung neoplasm (the surfaces “lung tumor”/“lung tumours”) join lung cancer, and breast carcinoma joins breast cancer. Which of those terms a mention lands on depends only on the wording the author happened to use, so splitting them across nodes is an artefact of ontology structure rather than a finding. Subtypes are deliberately not merged: non-small cell lung carcinoma, small cell lung carcinoma, lung adenocarcinoma, lung large cell carcinoma and pulmonary LCNEC remain separate nodes. The run prints what every node filter dropped — including the top un-normalized surfaces, which are gaps in disease.py/ chemical.py upstream, not exclusions made here. Shape encodes type (gene ● / disease ◆ / chemical ■), a Node type filter appears in the panel (an edge shows only when both endpoint types are ticked), and the score slider opens at ≥0.8 rather than ≥0.99 because most gene–disease edges sit between 0.5 and 0.8. Only gene names are drawn on the canvas — a disease or chemical name is long, repeats across many edges and would bury the gene symbols, so those nodes are drawn unlabelled and their names appear on hover (node tooltip, and in every edge tooltip) or on click. The set of labelled kinds is one constant, LABEL_KINDS. The “G” qualifying filter

The “G” rule set is all four of the conditions below (qualifies() in high_confidence_g.py) — rules 1–4 of the G_D_C filter, without rule 5. Since the gene-only view was retired it no longer gates the export or the graph — qualifies_multi() does — and now defines only the gene–gene slice reported per threshold as the G column of the console summary:

  1. score ≥ --score — model relation score at or above the threshold (export default 0.8).
  2. control = no — at least one GENETIC endpoint is annotated control: "no".
  3. not control = yes — neither endpoint is annotated control: "yes".
  4. no MKI67 — neither endpoint's hgnc_symbol is MKI67.
  5. disease/chemical context — not applied in this variant (this is the only difference from the G_D_C filter).

The filter that actually gates the export and the graph is qualifies_multi(): the same score rule, both endpoints must resolve to distinct nodes (a normalized id, surviving the hygiene tables), and rules 2–4 — which are about GENETIC endpoints — apply only when a gene is actually involved. Requiring “at least one endpoint annotated control: no” on a chemical–disease edge would drop every one of them, since neither endpoint can carry that flag.

Chemical identity: ChEBI first, then NCIt

ChEBI is a small-molecule ontology, so it has no term for a monoclonal antibody however cleanly the NER tagged it — and the corpus is full of them. Step 2's chemical.py therefore runs an NCIt pass after its ChEBI cascade and writes the leftovers to CHEMICAL/chemical_ncit.json; triples.py puts an ncit_label on the endpoint, never a chebi_label, so the two ontologies stay distinguishable; and node_of here accepts either. On this corpus that recovers 313 surfaces / 1,979 mentions that were previously discarded — icotinib, anlotinib (→ Catequentinib), inetetamab, BCT-100, OBI-992 — and the drop bucket is renamed chemical: no ChEBI or NCIt id to say what was actually tried.

Recognition was the other half of the same gap: the BioBERT chemical model tagged only 24% of named-antibody mentions, so step 2's NER now runs an INN-stem and NCIt lexicon pass (drug_lexicon.py, built by pipeline step 3), which takes that to 100%. Neither half helps alone: recognition without normalisation is dropped at the ChEBI gate, and normalisation without recognition never sees the mention.
