Step 2 (updated) — triples pipeline (gpu_bundle)

The step 2 pipeline rewritten to follow §8 “Suggested order of work” of gpu_bundle/BioRED_task_mapping.md: a second relation-extraction model, trained on BioRED (Luo et al. 2022, 10.1093/bib/bbac282), now runs alongside the BioInfer/PPI model, so the learned RE step can emit typed and signed edges (upregulator/activator, downregulator/inhibitor, binds, associated) instead of a single undirected interacts — and a comparison step produces the evidence for deciding whether that upgrade is real. The chain grows from 16 to 18 steps; everything the old pipeline did, it still does, byte-for-byte, when BioRED is skipped.

Calibration: per task now, not one global default

The probability calibrator is no longer a single default applied to whatever is being trained — it is resolved from the task, so the right one is picked without anyone having to remember it at the call site.

entry pointtaskcalibrator
run_re_pipeline.py (step 1) ppi (also chemprot / gad / ddi) isotonic — unchanged

In both run_re_pipeline.py and train_re.py the --calibration default is None and resolved after parsing: platt for --task biored, isotonic otherwise. An explicit --calibration isotonic|platt|none still wins, and the resolved value is printed in the startup [task] line. Where the fit happens is unchanged: the orchestrated path always invokes train_re.py --calibration none and fits the calibrator in run_re_pipeline.py's own step 3, so the trainer's default only applies when train_re.py is run directly — both follow the same rule either way. calibration.py itself is untouched: Platt was already a supported choice, only the default selection is new.

Why: isotonic regression is nonparametric and overfits small calibration sets — fine against BioInfer's ~780-row dev split, but BioRED's dev split is 100 abstracts, where it would fit a step function to a few hundred points and feed confidently wrong p_rel into the composite score. Platt scaling has two parameters and degrades gracefully.

Why collapse. Eight types over roughly 6,500 annotated relations is not 810 per class: Association, Positive_Correlation and Negative_Correlation dominate, while the four chemical-chemical bookkeeping types plausibly have tens of instances each. Split three ways, a class with ~30 instances has a handful in test, which makes its F1 noise and its learned boundary close to arbitrary. Those are exactly the classes that never become a graph edge with a sign, so folding them into Association raises per-class support and stops the metric being dominated by classes we do not use. The three that do upgrade the graph are the well-populated ones. The registry in train_re.py still maps all eight raw labels, so --biored-all-types trains the full label set without further edits.

Negative label. false, matching the ChemProt/DDI convention rather than the PPI 0. That matters downstream: relation_extraction.py auto-detects the negative class from a default set that already contains false, so RE_NEG_LABELS never has to be set.

The one real risk: BioRED relations are document-level. iter_instances() forms pairs strictly within a sentence, so a pair with a document-level relation produces a positive row in every sentence where both endpoints co-occur — including sentences that merely mention them. Recall loss is harmless (no row is emitted); the precision loss is the problem, and noisy labels hurt a small corpus more than a large one because there is no volume to average them out. Three defences, in the order the mapping doc recommends: (1) measure it — --sample-positives 50 and count how many rows actually assert the relation; that number is the ceiling on label quality. (2) --require-cue, which demotes cue-free positives. (3) the composite score in relation_extraction.py still multiplies p_rel by cue_factor, margin_factor and section_factor, so a confidently wrong p_rel is damped at scoring time regardless.

What --require-cue actually does

The flag reaches convert_split() and is passed straight through to iter_instances(), where it does exactly one thing:

label = label_for(task, rel, chemprot_eval_only, biored_collapse)
if require_cue and rel is not None and not RELCUE.search(connecting):
    label = label_for(task, None, chemprot_eval_only, biored_collapse)   # -> "false"
  • It only ever demotes. The guard is rel is not None, so it touches rows that have an annotated relation. A pair with no annotation is already negative and is never promoted.
  • connecting is the text strictly between the two entity spans (s_text[ae0:bs0]) — the same slice triples.py uses as its candidate predicate. A cue before the subject or after the object does not count. RELCUE is a copy of triples.py's stem list, so the training filter and the rule-based extractor agree on what a relation looks like.
  • The row count is unchanged; the label flips. In convert_split() that row moves from the pos list to neg — which also matters with --neg-ratio, whose cap is neg_ratio × len(pos): demoting positives shrinks the negative budget too, so the split gets smaller overall.
  • It is not gated by task. The CLI help says “biored:” because that is what it is for (document-level annotation), but with --task ppi the same filter would apply and emit 0 rather than false as the demoted label.

What it costs, measured on the fixture — each split goes from {Negative_Correlation 3, Positive_Correlation 1, Association 1, false 1} to {Negative_Correlation 2, Positive_Correlation 1, false 3}, i.e. two demotions:

rowlabel → labelverdict
@GENE$ and @GENE$ were both quantified by qPCR. Negative_Correlation → false correct — the document-level artefact caught
The @VARIANT$ variant was observed in patients with @DISEASE$. Association → false wrong — a real association whose phrasing ("was observed in patients with") carries no stem

That ratio is the entire decision, and it is why the default is off: a cue list cannot tell a genuinely cue-free assertion from a bare co-occurrence. Run --sample-positives 50 on the real corpus to see which error dominates before committing to it.

Precedence in exclusive mode is pair-specific > BioRED > RE_MODEL (global fallback). One consequence worth naming: with BioRED alone, no candidate pair is skipped for want of a model — including CHEMICAL–DISEASE, which the old routing table had no checkpoint for at all.

Additive mode double-counts if you let it. A pair scored by two checkpoints yields two triples in triples_re.json, distinguishable by predicate.model and joinable by pair_id. That is what makes step 17 possible, but it means the file is no longer one-triple-per-pair: filter by predicate.model (or re-run the step with --route-mode exclusive) before building a graph from it — unless the consumer merges them, which stage 3 now does; see below. The step 16 HTML summary says so explicitly, printing the distinct-pair count next to the triple count whenever the two differ.

What stage 3 does with it — high_confidence_g.py

The two verdicts only become a better graph if the graph builder reads them, and until now it did not: it categorized edges by polarity and never touched predicate.text, so every BioRED label collapsed into one indistinguishable edge, and with two checkpoints in the file its counts double-counted. Both are fixed in high_confidence_g.py, which is now the maintained step-3 entry point — high_confidence.py (the “G_D_C” variant) is deprecated: it still runs unchanged, and prints a notice saying exactly what it gets wrong.

1. The merge. --merge collapses the per-pair duplicates (joined on pair_id) into one triple:

--mergekeepslabel
union (default) every pair either model kept — BioRED-only edges included the typed one wherever BioRED fired; score = the higher of the two
gateonly pairs the binary model also kept typed where BioRED also fired — the stricter option for when BioRED-only edges (the ones with no second opinion) prove noisy
typedonly pairs BioRED kepttyped — BioRED replacing PPI outright
noneeverythingas written — pre-merge behaviour

Each merged triple carries models, corroborated and score_by_model, so “both models agreed on this edge” survives into the export rather than being averaged away. With a single checkpoint in the file every policy is a no-op.

2. Typed, signed edges. The graph now categorizes each edge by the relation the model predicted — activates / inhibits / binds / interacts / associated, prefixed not  when negated — with colour encoding the relation, negated edges dashed, and each sentence's own label in the tooltip (an edge shows its best-supported relation, so a minority reading stays visible). This is where the sign finally lands: A inhibits B and A activates B stopped being the same edge.

3. --nodes all — the multi-type graph. The gene-only view draws an edge only when both endpoints carry a single HGNC symbol, so BioRED's other pair types were scored, written to triples_re.json, and then silently discarded at graph-build time: on the reference run 649 of its 655 solo pairs (466 gene–disease, 117 chemical–gene, 29 chemical–disease, 24 chemical–chemical). Coverage gained at step 16 was not coverage gained in the graph. With --nodes all, DISEASE and CHEMICAL endpoints become nodes too, identified by their normalized id (mondo_label / chebi_label) so one entity is one node across documents:

viewnodesedgessigned edgesedges by node-type pair

Shape encodes type (gene ● / disease ◆ / chemical ■), a Node type filter appears in the panel, and the score slider opens at ≥0.8 rather than ≥0.99 because most gene–disease edges sit between 0.5 and 0.8. Outputs take an _M suffix, so the two views coexist. The gene–gene count is identical in both, as it must be.

Node hygiene: what the wider graph filters out, and why it is stated out loud

Opening the graph to three entity types means the normalization gaps become visible, so the node filters are curated and reported rather than silent. Each run prints what it dropped:

nodes kept: gene 806, disease 278, chemical 204
DISEASE_SURFACE overrides applied: 6 mention(s) (lcc)
DISEASE_MERGE (one disease, one node): lung neoplasm -> lung cancer x4, breast carcinoma -> breast cancer x2
endpoints dropped: gene: no HGNC symbol 361, disease: generic (DISEASE_IGNORE) 186,
                   disease: no MONDO id 38, chemical: no ChEBI id 22, gene: control / MKI67 11
top un-normalized surfaces (fix upstream, not here): CHEMICAL 'TBX3' x8, DISEASE 'tumoral' x3,
  DISEASE 'VM' x3, DISEASE 'HLF' x3, DISEASE 'HGNEC' x2, DISEASE 'LLC' x2, ...
  • Reused pipeline annotations, not new rules: control (genes), phenotype from DISEASE/disease.json, non_chemical from CHEMICAL/chemical.json — joined on the surface text, since those in-place flags never reach the RE triples.
  • DISEASE_IGNORE = neoplasm, cancer, os, matched against both surface and label. neoplasm is the entry that does the work — “tumor”/“tumors”/“tumour” all normalize onto it, 167 mentions, ~40% of all disease mentions — and deleting that one entry is how you get them back. os is surface-only (“overall survival”, an NER mislabel) and would never match a MONDO label, which is why the check reads both.
  • DISEASE_SURFACE corrects mappings that are wrong for this corpus instead of discarding the mention: lcc normalizes to leukoencephalopathy with calcifications and cysts, which here is large cell carcinoma.
  • DISEASE_MERGE folds MONDO terms that name the same disease at the same granularity into one node: lung carcinoma and lung neoplasm (the surfaces “lung tumor”/“lung tumours”) join lung cancer, breast carcinoma joins breast cancer. Which term a mention lands on depends only on the wording the author used, so splitting one disease across three nodes is an artefact of ontology structure, not a finding. Subtypes are deliberately not merged — non-small cell lung carcinoma, small cell lung carcinoma, lung adenocarcinoma, lung large cell carcinoma and pulmonary LCNEC stay distinct, because in a lung corpus that distinction is the point. On the reference run this took disease nodes 21 →  19 and gave lung cancer 17 supporting sentences instead of 15.
The report immediately paid for itself. Its first run showed 225 endpoints dropped for having no normalized id at all — SchB, AUY922, lung cancer, LCNELC, breast cancer, large - cell lung cancer — which turned out to be three distinct bugs upstream, not one coverage gap:
  1. A join bug in triples.py. disease.py and chemical.py aggregate their library keys through dash_normalize (dash glyphs unified, whitespace around - stripped), but the triple's surface is the verbatim NER text, and the lookup was exact. So 'large - cell lung cancer' never matched its own library entry 'large-cell lung cancer'. Both normalizers now retry the dash-normalized key — 24 endpoints recovered.
  2. A missing tie-break in disease.py. chemical.py had a label-preference guard (a surface hitting several terms but matching exactly one via that term's label resolves to it); disease.py never got it, so 'lung cancer' was written off as ambiguous between MONDO's lung cancer (label) and lung carcinoma (broad synonym). Porting the guard cut ambiguous surfaces from 19 to 9 and moved lung cancer, breast cancer and lymphoma into the single-match library.
  3. Genuinely absent abbreviations — curated: SchB → ChEBI's (+)-schisandrin B, AUY922 → luminespib, LCNELC → MONDO's pulmonary large cell neuroendocrine carcinoma.
Result: un-normalized disease endpoints 109 → 38, chemical 116 → 22, and the multi-type graph grew from 128 nodes / 151 edges to 151 nodes / 205 edges with 56 signed edges instead of 26 — without touching the models. The gene-only view is unchanged at 62 / 55, as it should be.

7. What was verified, and what was not

Verified on this machine (no GPU, no datasets, no network): the mapping functions and both new flags, exercised end-to-end through bigbio_to_re.py --input-json against a synthetic BioRED-shaped BigBIO-KB document — six entity types mapping to the right markers, the pair filter admitting exactly the annotated pair types, Conversion collapsing into Association, and a deliberately cue-free co-occurrence sentence ("TP53 and MDM2 were both quantified by qPCR") receiving a positive label without --require-cue and false with it. Also verified: train_re.py's label space on those TSVs, the --smoke template, the route and per-(pair, model) marker selection in relation_extraction.py, compare_re.py on synthetic scored triples, gpu.py --list, and that run_re_pipeline.py with no arguments still resolves to the exact previous PPI defaults. All six touched scripts byte-compile.

The _local_span() boundary fix (§3, §9) was checked case by case against the sentence that exposed it: dex is no longer matched inside dexamethasone; the full mention still matches; an annotated span that cuts a word realigns to the whole word; a correct span is untouched; and a mention ending on punctuation still places. The fixture conversion is byte-identical before and after the fix, so nothing regressed.
Not verified — needs the GPU box with internet. (a) The BioRED type strings themselves: run --print-types first (§5 step 1); this is §8's first instruction and it is deliberately still yours to run. (b) The real conversion's row counts and class balance. (c) Training, calibration and every number that follows from them. (d) Whether the document-level artefact is severe enough to need --require-cue — the hand-read decides that, and the tool for it now exists. (e) BioRED's novelty annotation (§7 of the mapping doc) is untouched: whether the BigBIO KB schema carries it through is still open, so nothing in the pipeline depends on it.

Model selection is also noisier here than on BioInfer: load_best_model_at_end picks an epoch on a 100-abstract dev split, so small dev-F1 differences should not be read as real. That is a reason to distrust the metric, not to avoid the corpus — which is precisely why step 17 compares the two models on our own sentences rather than on their respective test sets.

8. Notes

  • Nothing was removed. The BioInfer/PPI path is unchanged in behaviour and still the default; BioRED is additive in every sense — an optional step, an extra checkpoint, an extra route, an extra summary. If step 2 fails, the run degrades to the old 16-step pipeline plus a warning.
  • Two triple producers, now three verdicts. triples.py (13) stays rule-based; step 16 adds the learned scores — from the binary PPI model, the typed BioRED model, or both. The rule-based cue list and the BioRED training filter share the same RELCUE stems, so "what counts as a relation" is defined once.
  • Sign is the point. upregulator/activator vs downregulator/inhibitor is the difference between a graph that says two genes are connected and one that says which way. compare_re.py reports the signed-edge count as a headline figure for exactly that reason.
  • If more data is the goal, BioRED is not the cheapest route. The label-compatible corpora already supported — ChemProt/DrugProt for chemical-gene, GAD for gene-disease — have far more instances and overlap BioRED's pair types. BioRED is worth it for the sign and the type coverage, not for volume.
  • Source. Luo L, Lai P-T, Wei C-H, Arighi CN, Lu Z. BioRED: a rich biomedical relation extraction dataset. Briefings in Bioinformatics 23(5):bbac282, 2022. doi:10.1093/bib/bbac282, PMID 35849818, data at github.com/ncbi/BioRED. Full design notes and the residual open questions are in gpu_bundle/BioRED_task_mapping.md.

Result of the read: the document-level artefact is mild on this corpus, and --require-cue was NOT adopted. Two counts decided it, over the 49 fully printed rows:

measurerowswhat it says

The reason the filter overshoots is the window limitation named in §4: RELCUE reads only the text between the two entities, while biomedical titles — which dominate this sample, and which are nothing but assertions — routinely put the verb before the subject or after the object.

Decision: convert without --require-cue and let the composite score do the damping — cue_factor, margin_factor and section_factor in relation_extraction.py still discount a confident but cue-free prediction at scoring time, which is the defence that costs no training data. Trading ~24 positives per 49 to remove ~4 bad ones is the wrong side of §6's per-class-support worry on a corpus this size. Note this is a corpus-specific finding: the same read on a full-text corpus, where methods sentences survive, could easily go the other way — which is why the flag stays.

Two incidental findings from the same read. (a) Pair coverage looks right: the sample is dominated by CHEMICAL–DISEASE and GENE–DISEASE, including the CHEMICAL–DISEASE pairs the old routing table had no checkpoint for at all. (b) A blinding artefact, since fixed: row 31 came out as @CHEMICAL$amethasone-induced — the marker replaced only dex of dexamethasone. That was _local_span()'s fallback in bigbio_to_re.py: when the annotated offsets do not line up it did ptext.find(txt), which matches a short entity string inside a longer word and corrupts the training sentence. Both placement routes now require word-boundary alignment (checked only on the mention's own word-character edges, so -catenin or (RELN) are unaffected); an annotated span that cuts a word retries as a text search, and a mention that cannot be placed cleanly is skipped rather than blinded half-way, with both counts reported in a [spans] line at the end of the conversion. Row 5's @GENE$+IFN-g+ was not an instance of this — that is the correct blinding of CD4 in “Long-Lived CD4+IFN-g+ T Cells”, with the +IFN-g+ simply being the text that follows.
